1. El Amanecer: Bitcoin y el Modelo UTXO

El dinero electrónico P2P: la mecánica de "cambio" en UTXO y por qué Bitcoin no puede albergar dApps aún.

📌 Idea Central para la Cátedra: Bitcoin funciona bajo un sistema de "billetes y cambio" (UTXO) diseñado para transferir valor P2P. Debido a que su lenguaje carece de bucles y no recuerda el estado de la red, Bitcoin nativo NO puede ejecutar contratos inteligentes complejos ni soportar aplicaciones descentralizadas (dApps).
El Modelo UTXO: La Mecánica del "Cambio"

Bitcoin no tiene cuentas con saldo (como una libreta bancaria), sino Unspent Transaction Outputs (salidas no gastadas):

💵 Analogía del Billete Físico: Si tienes un billete de $50.000 y pagas un café de $10.000, entregas el billete completo. La tienda recibe $10.000 y a ti te devuelven un billete de $40.000 de "cambio".
En Bitcoin es idéntico: el UTXO de 1 BTC se destruye, 0.2 BTC van al receptor y se genera un nuevo UTXO de cambio (0.8 BTC) de vuelta a tu billetera.
  • Gasto Atómico: Un UTXO se consume al 100% o no se gasta.
  • Prevención del Doble Gasto: Los nodos solo verifican si el UTXO ya fue consumido en el grafo global.
¿Por qué NO permite dApps aún?

Para que existan dApps (DEXs como Uniswap, préstamos como Aave o tokens ERC-20), se requiere lógica arbitraria. Bitcoin no lo permite por diseño:

  • Script NO es Turing-Completo: Se eliminaron bucles (`OP_LOOP`) para evitar ataques de denegación de servicio (bucles infinitos).
  • Ceguera de Estado (*State-Blindness*): Un script de Bitcoin solo evalúa si una clave puede gastar ese UTXO específico; no puede leer otras transacciones, ni almacenar variables globales, ni registrar balances compartidos.
El Vacío que Llenó Ethereum: Para crear tokens fungibles y dApps programables, el mundo necesitaba una máquina virtual con estado persistente (EVM). En Bitcoin en L1, esto aún no es posible de forma nativa.

2. Criptografía y Estructuras de Datos en Blockchain

Garantías matemáticas de inmutabilidad, ordenamiento temporal y mecanismos de consenso.

Criptografía Asimétrica

Basada en curvas elípticas sobre cuerpos finitos:

  • Curva secp256k1: $y^2 = x^3 + 7 \pmod p$.
  • Firma Digital ECDSA: Garantiza autenticidad, no repudio e integridad sin revelar la clave privada ($k$).
  • Derivación de Direcciones: En Ethereum, se aplica la función hash Keccak-256 a la clave pública desprovista de prefijo y se toman los últimos 20 bytes (160 bits).
Árboles de Merkle-Patricia

Estructura criptográfica para verificación eficiente:

  • Pruebas de Inclusión $O(\log n)$: Un cliente ligero puede verificar si una transacción pertenece a un bloque sin descargar la cadena entera.
  • Raíz de Estado (*State Root*): Cada cabecera de bloque contiene el hash del Trie de Estado, asegurando que cualquier discrepancia de datos altere la raíz criptográfica.
Consenso: PoW vs. PoS

Resolución del problema de los generales bizantinos:

  • Proof of Work (PoW): Gasto termodinámico mediante hashing intensivo; la cadena con mayor trabajo acumulado es la verdad canónica.
  • Proof of Stake (PoS - Ethereum Gasper): Validadores con 32 ETH en garantía; penalización económica destructiva (*slashing*) en caso de conducta deshonesta o firma doble.
Principio Fundamental de Inmutabilidad: La alteración retroactiva de un solo byte en un bloque histórico invalida su hash y el de todos los bloques subsiguientes, exigiendo rehacer todo el consenso computacional de la red.

3. El Salto a Ethereum: La Computadora Mundial

Turing-completitud, el modelo basado en cuentas y el control de ejecución determinista vía Gas.

Arquitectura de la EVM (Ethereum Virtual Machine)

Máquina de estados determinista basada en pila con palabras de 256 bits (optimizadas para hashes criptográficos):

  • Stack: Pila de ejecución LIFO con un límite de 1024 niveles.
  • Memory: Arreglo de bytes volátil de un solo llamado; su costo en gas escala cuadráticamente con el tamaño.
  • Storage: Mapa persistente de clave-valor de 256 bits a 256 bits almacenado en el disco de los nodos. Es el recurso más costoso de la red (`SSTORE` = hasta 20,000 gas).
  • Calldata: Área de solo lectura inmutable donde residen los argumentos de la transacción.
Cuentas y la Solución al Halting Problem
Tipo de Cuenta Control Almacenamiento
EOA (Externas) Clave privada humana Sin código ni storage
Contratos Bytecode de la EVM Storage Trie propio
El Problema de la Parada (Alan Turing, 1936):
Es matemáticamente imposible predecir si un programa arbitrario entrará en un bucle infinito. Ethereum resuelve esto imponiendo una tasa económica finita (Gas): cada opcode consume una cuota exacta; si el gas prepagado se agota, la ejecución revierte inmediatamente sin alterar el estado.

4. El Caos Pre-ERC-20 y el EIP-20 (Noviembre 2015)

Cómo la estandarización de interfaces resolvió la fragmentación y permitió el auge de las finanzas descentralizadas.

El Problema de la Fragmentación

Antes de noviembre de 2015, cada desarrollador creaba sus propios contratos de token con nombres arbitrarios de funciones:

  • Token A: transferCoin(address, uint)
  • Token B: sendToken(address, uint)
  • Token C: pay(address, uint)
Consecuencia Sistémica: Los exchanges y billeteras (como MetaMask o Ledger) debían programar integraciones a la medida por cada token emitido, impidiendo la interoperabilidad composable (Legos de Dinero).

EIP-20: Propuesta formal presentada por Fabian Vogelsteller y Vitalik Buterin para fijar una Interfaz Binaria de Aplicación (ABI) universal.

Diferencia Ontológica: ETH Nativo vs. Token ERC-20
Propiedad Ether Nativo (ETH) Tokens ERC-20
Capa Capa 1 (Consenso / Protocolo) Capa 2 (Aplicación / Bytecode)
Gestión de Saldo Campo nativo de la cuenta mapping(address => uint256) interno
Comisiones de Red Única moneda aceptada para Gas No pueden pagar gas nativo (sin ERC-4337)
Comportamiento Transfiere valor con opcodes nativos Llamada a función de contrato
Definición de Fungibilidad: Cada unidad de token es idéntica, indivisible cualitativamente e intercambiable por otra unidad equivalente, sin historial diferenciador en el balance.

5. Especificación Formal de la Interfaz IERC20

Métodos requeridos, aritmética de coma fija y desglose de firma de funciones en Solidity.

Interfaz Formal en Solidity (IERC20)
interface IERC20 { // Métodos de consulta de estado function totalSupply() external view returns (uint256); function balanceOf(address account) external view returns (uint256); function allowance(address owner, address spender) external view returns (uint256); // Métodos de mutación de estado function transfer(address to, uint256 value) external returns (bool); function approve(address spender, uint256 value) external returns (bool); function transferFrom(address from, address to, uint256 value) external returns (bool); // Eventos de indexación event Transfer(address indexed from, address indexed to, uint256 value); event Approval(address indexed owner, address indexed spender, uint256 value); }
Aritmética de Punto Fijo y Decimales

¿Por qué 18 decimales?

  • La EVM no posee soporte nativo para números de coma flotante (*float/double*) para evitar indeterminismos en arquitecturas de procesador divergentes.
  • Todos los saldos son enteros puros (`uint256`).
  • 1 Token completo con 18 decimales se representa en almacenamiento como:
    1.0 Token = 1000000000000000000 unidades ($10^{18}$)

6. El Sistema de Eventos y la Capa de Indexación Off-Chain

Mecánica interna de los opcodes LOG, filtros Bloom y sincronización con The Graph.

Opcodes LOG y Tópicos Indexados

Cuando un contrato emite un evento, la EVM ejecuta los opcodes `LOG0` a `LOG4`:

event Transfer(
  address indexed from, // Topic 1 (32 bytes)
  address indexed to, // Topic 2 (32 bytes)
  uint256 value // Data payload (no indexado)
);
  • Topic 0: Hash Keccak-256 de la firma canónica: `keccak256("Transfer(address,address,uint256)")`.
  • Topics 1 y 2: Parámetros con el modificador `indexed` guardados en la estructura del log para búsquedas directas.
  • Eficiencia Económica: Emitir un log cuesta 375 gas (+ 375 por topic + 8 gas/byte), en contraste con los 20,000 gas de escribir en el storage con `SSTORE`.
Filtros Bloom e Indexación Externa

Los smart contracts no pueden leer logs emitidos previamente (los logs son de solo escritura para la EVM). ¿Cómo se consultan?

  • Filtro Bloom del Bloque (2048 bits): Estructura probabilística en la cabecera que permite saber en $O(1)$ si un contrato o tópico podría estar presente en el bloque, descartando bloques irrelevantes sin abrirlos.
  • Indexadores Descentralizados (The Graph / Goldsky): Nodos indexadores procesan los logs en tiempo real para poblar bases de datos GraphQL relacionales.
  • Billeteras (MetaMask): Reconstruyen el historial de transacciones escuchando los eventos `Transfer` donde el usuario es remitente o receptor.
Regla de Oro: Si una transferencia no emite el evento `Transfer`, ningún explorador ni billetera registrará visualmente la actualización del balance.

7. Flujo Operativo: Transferencia Directa vs. Delegada

El patrón Approve-TransferFrom y la mecánica de interacción con AMMs y protocolos DeFi.

El Problema del Receptor Ciego: Si un usuario envía tokens ERC-20 a un contrato con transfer(), el contrato no recibe notificación ni ejecuta código de recepción; los tokens quedan atrapados irreversiblemente.
Fase 1: Autorización Usuario → token.approve() El propietario autoriza al contrato gestor (e.g. Uniswap Router) a retirar un monto determinado modificando _allowances[owner][router].
Fase 2: Ejecución Usuario → router.swap() El usuario llama la lógica de negocio del protocolo. El router verifica condiciones y precios.
Fase 3: Deducción router → transferFrom() El router extrae los tokens de la cuenta del usuario, descuenta el allowance y los transfiere a la pool de liquidez.
El Riesgo de Infinite Allowance

Muchos frontends solicitan aprobar type(uint256).max ($2^{256}-1$) para evitar que el usuario deba firmar y pagar comisiones en cada interacción.

Vulnerabilidad Sistémica: Si el contrato autorizado sufre un exploit o contiene una puerta trasera, el atacante puede drenar todos los tokens del usuario en cualquier momento futuro.
Mitigación Moderna: EIP-2612 (Permit)

Permite autorizaciones sin transacciones directas en blockchain mediante firmas criptográficas off-chain (EIP-712):

  • El usuario firma un mensaje estructurado con su billetera (sin pagar gas).
  • El contrato recibe la firma y ejecuta permit() + transferFrom() en una única transacción atómica.

8. Seguridad Crítica y Vulnerabilidades en ERC-20

Condiciones de carrera en la mempool, desbordamientos de enteros y prevención de reentrancia.

Front-Running en Approve

Condición de Carrera en Mempool:

  1. Alice tiene cuota de 100 para Bob. Decide bajarla a 50.
  2. Bob monitorea la mempool pública y detecta la transacción pendiente.
  3. Bob envía un transferFrom(100) con mayor prioridad de gas.
  4. La transacción de Bob entra primero (gasta 100); luego se confirma la de Alice (fija cuota en 50). Total extraído: 150 tokens.
Solución: Exigir reseteo previo a 0: approve(0) antes de asignar un nuevo monto.
Desbordamiento Aritmético

El Hack de BeautyChain (BEC, 2018):

uint256 amount = cnt * _value;
// cnt = 2, _value = 2^255
// amount desbordó a 0

El atacante evadió el control de saldo y minteó $1.2 \times 10^{77}$ tokens de la nada.

  • Histórico: Uso obligatorio de la librería SafeMath de OpenZeppelin.
  • Moderno: A partir de Solidity 0.8.0, las operaciones aritméticas integran verificación automática y revierten ante desbordamiento sin costo adicional.
Reentrancia y Patrón CEI

Ocurre cuando una llamada externa toma el control del hilo de ejecución antes de actualizar el saldo local:

Patrón Checks-Effects-Interactions:
  1. Checks: Validar balances y parámetros (`require`).
  2. Effects: Modificar el balance local en storage.
  3. Interactions: Ejecutar llamadas externas (`transfer`, hooks).

Uso de cerrojos de exclusión mutua: modificador nonReentrant de OpenZeppelin.

9. Anomalías en Producción y OpenZeppelin v5

Discrepancias del estándar en la vida real y la arquitectura de consolidación con _update().

Anomalías Comunes en la Industria
  • Tokens Sin Retorno Booleano (USDT en Ethereum): El contrato de Tether omite retornar un booleano en transfer(). Un contrato que use IERC20 estricto revertirá al interactuar con USDT.
    Solución: Uso obligatorio de la librería SafeERC20 de OpenZeppelin.
  • Fee-on-Transfer: Tokens que aplican un impuesto de quema en cada transferencia. El monto recibido es menor que el enviado, quebrando asunciones contables en AMMs.
  • Rebasing Tokens (stETH de Lido): Modifican los balances de todas las cuentas automáticamente al rebalancear recompensas sin emitir eventos Transfer individuales.
Arquitectura de Consolidación en OpenZeppelin v5

En OpenZeppelin v5, todas las operaciones de balance convergen en una única función interna centralizada:

function _update( address from, address to, uint256 value ) internal virtual { if (from == address(0)) { _totalSupply += value; // Minting } else { _balances[from] -= value; } if (to == address(0)) { _totalSupply -= value; // Burning } else { _balances[to] += value; } emit Transfer(from, to, value); }
Ventaja de Diseño: Cualquier hook o auditoría de seguridad (pausas, listas negras, snapshots de gobernanza) se sobrescribe en un solo punto del código.

11. Conclusiones y Líneas de Investigación en el Semillero

El futuro de la programabilidad de tokens: Account Abstraction, Rollups y verificación formal.

Horizontes Tecnológicos del Estándar
  • ERC-4337 (Account Abstraction): Los contratos Paymaster permiten que los usuarios paguen las tarifas de red directamente con el token ERC-20 transferido, eliminando la necesidad de adquirir y custodiar ETH previo.
  • Escalabilidad en Capa 2 (L2 Rollups): Migración masiva de transferencias de tokens a Arbitrum, Optimism y ZK-Rollups, reduciendo las comisiones en más de un 95%.
  • Privacidad Criptográfica: Integración de pruebas de conocimiento cero (zk-SNARKs) para transferencias confidenciales de activos institucionales.
Líneas de Trabajo para el Semillero UdeA
  • Verificación Formal: Modelado matemático con herramientas como Certora y K-Framework para demostrar la ausencia absoluta de bugs en contratos de tesorería universitaria.
  • Tokenización de Activos Campus: Proyectos piloto de economía circular y créditos fraccionados de energía solar en la Facultad de Ingeniería.
  • Desarrollo Seguro: Implementación de suites completas de pruebas automatizadas con Hardhat, Foundry y análisis estático con Slither.
Mensaje Institucional: El estándar ERC-20 demostró que el verdadero poder de una blockchain no radica en la especulación de precios, sino en la estandarización universal de protocolos computacionales abiertos.
