01 / Génesis Computacional • Modelo de Grafo UTXO

Bitcoin (2008-2009): El Modelo UTXO y sus Límites

Satoshi Nakamoto solucionó el doble gasto mediante ordenamiento en bloques, pero delimitó conscientemente el poder computacional de la red.

Grafo Acíclico Dirigido (DAG) Unspent Transaction Output

Bitcoin no almacena cuentas ni balances acumulados. El registro contable es un árbol de salidas no gastadas (UTXO) que se consumen atómicamente y generan nuevas salidas:

[Tx_In: UTXO 1.0 BTC] ──► [ScriptSig + ScriptPubKey] ──► [UTXO 0.3 BTC Bob]
                                                └──► [UTXO 0.7 BTC Vuelto Alice]
Bitcoin Script: Deliberadamente No Turing-Completo
  • 1. Ausencia de Bucles: Carece de FOR o WHILE. Evaluación $O(n)$ en tiempo lineal estricto sin posibilidad de bucle infinito.
  • 2. Ceguera de Estado (State-blindness): Un script no puede inspeccionar datos globales, oráculos ni balances de otras UTXOs.
  • 3. Sobrecarga para Activos: Emitir tokens requirió trucos como OP_RETURN (Omni Layer en 2014 para los primeros USDT).

Lección de Arquitectura de Sistemas

El diseño de Bitcoin optimizó la robustez de una red monetaria pura. Sin embargo, impidió la ejecución de contratos con estados dinámicos persistentes:

A
Pila LIFO Simple: Opcodes elementales (OP_DUP, OP_HASH160, OP_CHECKSIG).
B
Sin Memoria Entre Bloques: El estado se extingue al validarse la firma.
C
La Necesidad: Una máquina con estado persistente capaz de computar cualquier algoritmo.
📖 "Bitcoin demostró la viabilidad del libro contable sin intermediarios; Ethereum nació para convertirlo en un computador universal."
02 / Pilares Teóricos • Criptografía & Consenso

Fundamentos Criptográficos y Evolución del Consenso

La inmutabilidad del registro descentralizado descansa en asimetría matemática, árboles Merkle-Patricia y el teorema de consenso bizantino.

Criptografía Asimétrica

Firmas ECDSA sobre la curva secp256k1. El usuario firma transacciones con su clave privada $k$; la red verifica con la clave pública $K = k \cdot G$.

Dirección = Keccak-256(PubKey)[12:] (160 bits)

Árboles Merkle-Patricia

Verificación e integridad criptográfica en tiempo logarítmico $O(\log n)$. Permite validar la inclusión de transacciones y estados con pruebas compactas (Merkle Proofs).

Efecto avalancha: 1 bit altera el StateRoot

Consenso PoW vs PoS

Transición de la fuerza bruta termodinámica (Proof of Work) al consenso económico Proof of Stake (Casper FFG): validadores arriesgan 32 ETH bajo pena de slashing.

99.95% menos energía Finalidad LMD-GHOST

03 / La Computadora Mundial • Arquitectura EVM

El Salto a Ethereum: La Máquina de Estados de Turing

Vitalik Buterin y Gavin Wood (Yellowpaper, 2014) formalizan la Ethereum Virtual Machine: cuentas, storage trie y el paradigma de gas.

Formalismo del Modelo Basado en Cuentas

El estado global $\sigma$ es un mapeo formal entre direcciones de 160 bits y tuplas de estado:

σ[address] = (nonce, balance, storageRoot, codeHash)
EOA (Externally Owned): Clave privada. Sin código (codeHash = keccak("")). Inicia transacciones.
Contract Account: Gobernado por Bytecode. Almacenamiento persistente propio.

El Gas y el Halting Problem de Alan Turing (1936)

Al ser la EVM Turing-completa, es matemáticamente imposible predecir si un programa arbitrario terminará o entrará en bucle infinito. Solución criptoeconómica del Gas:

• Cada opcode tiene costo determinista (ADD: 3 gas, SSTORE: 20,000 gas).
• Si el cómputo sobrepasa el gasLimit, la EVM lanza OutOfGas y revierte todos los cambios de estado atómicamente.

04 / Génesis del Estándar • 19 Noviembre 2015

El Caos Pre-ERC-20 y la Propuesta EIP-20

Fabian Vogelsteller y Vitalik Buterin crearon el estándar rector para poner fin a la fragmentación de interfaces en Ethereum.

El Problema de la Incompatibilidad
Fragmentación en 2015
// Contrato Alice: function sendCoin(address to, uint256 val) public; function coinBalance(address who) public view; // Contrato Bob: function transferTokens(address recv, uint256 amt) public; function checkFunds(address owner) public view;

Cada token inventaba sus propias funciones. Wallets y Exchanges tenían que reprogramar su código para cada moneda. EIP-20 unificó la ABI universal.

Diferencia Ontológica Fundamental
Criterio Ether Nativo (ETH) Token ERC-20
Capa Capa 1 (Consenso base) Capa de Aplicación (Smart Contract)
Storage Campo balance nativo en la EVM mapping(address => uint256) interno
Transferencia Opcode CALL con msg.value Llamada al contrato del token (transfer)
Receptor Detona receive() / fallback() El receptor no es invocado ni notificado
✨ Fungibilidad: Cada unidad de token en el balance es matemática y comercialmente indistinguible de cualquier otra.
05 / Especificación Formal • Interfaz IERC20

Anatomía Técnica del Estándar ERC-20

Una arquitectura minimalista de 3 métodos opcionales de metadatos, 2 funciones de lectura y 4 métodos de mutación de saldos.

IERC20.sol (Especificación Formal)
Solidity 0.8.20
interface IERC20 { // 1. Metadatos Opcionales (UI / Clientes) function name() external view returns (string memory); function symbol() external view returns (string memory); function decimals() external view returns (uint8); // 2. Funciones de Lectura (View / Sin costo de Gas en RPC) function totalSupply() external view returns (uint256); function balanceOf(address account) external view returns (uint256); // 3. Métodos de Mutación de Estado (Consumen Gas) function transfer(address to, uint256 value) external returns (bool); function allowance(address owner, address spender) external view returns (uint256); function approve(address spender, uint256 value) external returns (bool); function transferFrom(address from, address to, uint256 value) external returns (bool); }

Aritmética de Punto Fijo (Fixed-point)

La EVM no admite coma flotante (float/double) para prevenir discrepancias del estándar IEEE 754 entre diferentes CPUs.

1.0 TOKEN (18 decimales):
1000000000000000000 (1 × 10¹⁸ Wei-units)

1.0 USDC (6 decimales):
1000000 (1 × 10⁶ micro-unidades)

Invariante de Conservación Monetaria

En ausencia de mint o burn, la suma de balances debe ser idéntica al suministro total:

totalSupply = ∑ balanceOf(addressᵢ)
06 / La Capa de Eventos • Logs & The Graph

La Capa de Eventos, Opcodes de Logs e Indexación Off-Chain

Cómo la EVM emite registros inmutables de bajo costo para que billeteras, exploradores y subgrafos sincronicen transacciones en tiempo real.

Eventos Estándar Obligatorios
event Transfer(address indexed from, address indexed to, uint256 value); event Approval(address indexed owner, address indexed spender, uint256 value);

La directiva indexed genera Topics de 32 bytes en la cabecera del registro para búsquedas de alta velocidad en clientes RPC.

Estructura del Opcode LOG3 en la EVM

Topic 0: keccak256("Transfer(address,address,uint256)") = 0xddf252ad...b3ef
Topic 1: Remitente (from address padded a 32 bytes)
Topic 2: Destinatario (to address padded a 32 bytes)
Data (no indexada): uint256 value (monto transferido)

Eficiencia de Gas y Filtros Bloom

GAS
Bajo Consumo: Un log cuesta ~375 gas + 8 gas/byte vs 20,000 gas de un SSTORE en el Storage Trie.
BLOOM
Filtro Bloom de 2048 bits: Incrustado en el Block Header. Los clientes evalúan si el bloque contiene eventos en tiempo $O(1)$.
GRAPH
The Graph (Subgraphs): Indexa eventos Transfer/Approval en GraphQL para alimentar frontends descentralizados al milisegundo.
⚠️ Principio de Diseño: Los contratos inteligentes no pueden leer logs en tiempo de ejecución; son exclusivamente para indexadores externos.
07 / Dinámica de Protocolos • DeFi Interoperability

Flujo Operativo: Transferencia Directa vs Delegada (DEXs)

La ceguera de contratos receptores en transferencias directas y la invención del patrón approve / transferFrom que hizo posible Uniswap.

Patrón Atómico de 2 Fases (Uniswap Router) DEX Mechanics
Fase 1: Transacción de Aprobación (approve)
Alice ──► USDC.approve(UniswapRouter, 1000) ──► Token Storage
Se registra: allowances[Alice][UniswapRouter] = 1000
▼ Alice firma Tx 2 (Swap) ▼
Fase 2: Ejecución e Intercambio (swap)
Alice ──► Router.swapExactTokens(...) ──► Pool AMM
1. Router ejecuta USDC.transferFrom(Alice, Pool, 1000)
2. Pool computa la curva de producto constante x · y = k
3. Pool transfiere DAI.transfer(Alice, 998) a la billetera de Alice
🔒 Ceguera de Contrato: Si Alice usa transfer() directamente al DEX, el contrato del DEX no ejecuta código y no sabe a qué usuario acreditar la operación, bloqueando los fondos para siempre.
Vector de Riesgo Sistémico

El Riesgo de Infinite Allowance

Para evitar pagar tarifas de gas en cada operación, las DApps solían solicitar aprobación máxima:

type(uint256).max = 2²⁵⁶ - 1
≈ 1.1579 × 10⁷⁷ tokens
💥 Consecuencia: Si el contrato aprobado sufre un exploit, el hacker puede invocar transferFrom(victima, hacker, balanceCompleto) y vaciar la billetera años después de la última interacción.
Herramienta de auditoría activa: Revoke.cash
08 / Auditoría y Hackeos • Seguridad de Smart Contracts

Seguridad Crítica: Trilogía de Vulnerabilidades

Condiciones de carrera en mempool, desbordamientos de enteros que evaporaron millones y los patrones de reentrancia en Solidity.

Race Condition en Mempool

Front-Running en Approve

Alice reduce el allowance de Bob de 100 a 50. Bob detecta la Tx en la Mempool y emite un transferFrom con gas superior para gastar 100 antes de que se aprueben los nuevos 50. Total extraído: 150.

Mitigación: Reset a 0 primero, o firmas off-chain permit() (EIP-2612 / EIP-712).
Exploit BeautyChain (BEC)

Desbordamiento Aritmético

En 2018 el token BEC multiplicó destinatarios por valor en batchTransfer. Al exceder $2^{256}$, el cálculo dio 0. Pasó la validación y acreditó billones de tokens a dos cuentas atacantes.

Mitigación: SafeMath en versiones previas, y Solidity 0.8+ nativo (Panic automático).
Reentrancy & CEI

Checks-Effects-Interactions

Invocaciones a contratos externos antes de decrementar el saldo permiten al atacante reingresar a la función y drenar fondos múltiples veces.

Mitigación: Mutex nonReentrant de OpenZeppelin y descontar balances ANTES de llamadas externas.
Solidity < 0.8.0 Obligatorio usar SafeMath.sol (sobrecosto en gas por funciones de biblioteca).
Solidity ≥ 0.8.0+ Protección por compilador con reversión inmediata. Uso de unchecked {} para optimizar gas probado.
09 / Ingeniería en Producción • OpenZeppelin Contracts

Casos Especiales en Producción y OpenZeppelin v5

Tokens que cobran impuestos, saldos dinámicos de staking y la arquitectura unificada en la rutina interna _update().

Fee-on-Transfer (Deflacionarios)
Cobran o queman un 1-5% en cada transferencia. El destinatario recibe menos del monto especificado, descalibrando pools que no recalculan balances con delta real.
Rebasing Tokens (stETH, AMPL)
Los balances aumentan o disminuyen algorítmicamente para reflejar rendimientos de staking de la red sin emitir eventos Transfer individuales.
USDT Missing Return Value
Tether USDT en Ethereum no retorna un bool en transfer. La solución industrial obligatoria es la librería SafeERC20 de OpenZeppelin.
OpenZeppelin v5.0 Core Pattern _update() Virtual Hook

En OpenZeppelin v5, transfer, mint y burn convergen en una sola función protegida y virtual:

function _update(address from, address to, uint256 value) internal virtual { if (from == address(0)) { _totalSupply += value; // Minting } else { uint256 fromBalance = _balances[from]; if (fromBalance < value) revert ERC20InsufficientBalance(); unchecked { _balances[from] = fromBalance - value; } } if (to == address(0)) { unchecked { _totalSupply -= value; } // Burning } else { unchecked { _balances[to] += value; } } emit Transfer(from, to, value); }
✓ Un único punto de entrada para auditorías de seguridad, extensiones y snapshots de votación.

Conclusiones y el Futuro: Account Abstraction & L2s

La genialidad de ERC-20 residió en su inmutabilidad y simplicidad. El futuro amplía sus capacidades mediante ecosistemas modulares.

ERC-4337: Account Abstraction

Los contratos Paymaster permiten abonar el gas de la red directamente con el mismo token ERC-20 que se envía (ej. pagar tarifas con USDC), suprimiendo la necesidad de fondear ETH.

UX Libre de Fricción

Rollups de Capa 2

Redes como Arbitrum, Optimism y zkSync reducen el costo de transacción de tokens en más de un 95%, permitiendo micropagos e inclusión financiera global.

Escalabilidad Masiva

Tokenización RWA Institucional
