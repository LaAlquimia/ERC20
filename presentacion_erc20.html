2. De Bitcoin a Ethereum: Del Libro UTXO a la EVM

La transición de un historial de billetes no gastados sin estado global a una computadora determinista con almacenamiento persistente y gas.

El Modelo UTXO de Bitcoin (2008)
  • Analogía del Cambio en Efectivo: Si tienes un billete de $50 y compras algo de $30, no editas el billete; lo destruyes por completo y se crean dos salidas no gastadas (UTXOs): $30 para el vendedor y $20 de cambio para ti.
  • Sin Estado Global: Bitcoin no guarda una tabla con saldos de usuarios. Solo existe el conjunto de transacciones no gastadas (UTXO Set).
  • Script No Turing-Completo: Se omitieron bucles deliberadamente (sin OP_LOOP) para evitar el problema de la parada (Halting Problem).
  • Imposibilidad de dApps: No permite lógica de estado compartida (pools de liquidez, subastas, tokens multi-usuario).
La Máquina Virtual de Ethereum - EVM (2015)
  • Computadora de Estado Mundial: Un único entorno de ejecución cuasi-Turing completo replicado por miles de nodos validadores sincronizados.
  • Cuentas con Almacenamiento Persistente: Las cuentas de contrato tienen un storage de clave-valor (256 bits a 256 bits) que persiste en disco.
  • Mecanismo de Gas: Cada opcode cuesta gas. Resuelve el problema de la parada: bucles infinitos agotan el gas y revierten la transacción de inmediato.
  • Componibilidad Universal: Cualquier contrato puede invocar a otro contrato en una sola transacción atómica, habilitando DeFi y dApps complejas.

3. Criptografía en Acción: Identidad y Verificación On-Chain

Derivación asimétrica de cuentas y la inmutabilidad instantánea del Árbol de Merkle con ejemplos visuales reales.

Pipeline de Derivación ECDSA (secp256k1)
1. Clave Privada (k - 256 bits) 0x4c859d1a3b8e720fa942c169823f40b284e5a9601d3a51f2b604... Entropía aleatoria pura generada off-chain. Jamás se comparte.
↓ Multiplicación Escalar en Curva: K = k · G (Unidireccional) ↓

↓ Truncado: Tomar los últimos 20 bytes (160 bits) ↓

4. El Caos Pre-ERC-20 (2015) vs La Estandarización EIP-20

De la fragmentación total a la convención universal, y la distinción ontológica entre ETH nativo y tokens de contrato.

El Caos Pre-2015 y la Propuesta EIP-20
  • Anarquía de Métodos: Antes de nov. 2015, cada proyecto inventaba su propia interfaz: unos usaban transferCoin(), otros giveAsset() o checkFunds().
  • Fricción Total: Wallets (Mist, MetaMask) e incipientes exchanges (EtherDelta) tenían que programar conectores a medida para cada token individual.
  • EIP-20 (Fabian Vogelsteller & Vitalik Buterin): Estandarizó 6 funciones mínimas (totalSupply, balanceOf, transfer, transferFrom, approve, allowance) y 2 eventos universales.
  • La Magia de la Componibilidad: Permitió que Uniswap o Aave interactúen con cualquier token presente o futuro sin cambiar una sola línea de código.
Diferencia Ontológica Fundamental
ETH Nativo (Protocolo L1 - Capa Base)

Activo nativo de la red Ethereum. Forma parte intrínseca de la cuenta en el cliente (account.balance). Se transfiere con los opcodes CALL o SELFDESTRUCT. NO tiene código de contrato ni emite eventos de Log (de ahí la necesidad de WETH).

Token ERC-20 (L2 Lógico - Smart Contract)

NO es dinero nativo. Es únicamente una tabla hash en la memoria de estado (mapping(address => uint256) private _balances) dentro de un smart contract específico. Su valor y existencia dependen estrictamente de su lógica programada.

5. Código Base: Almacenamiento y Eventos ERC-20

Estructura en storage de la EVM, slots de memoria y emisión de logs para indexación off-chain.

Arquitectura de Storage y Registro
  • Tabla de Balances: mapping(address => uint256) private _balances. Cada clave de 20 bytes se hashea con Keccak-256 para ubicar su slot de 32 bytes en disco.
  • Matriz de Delegación: mapping(address => mapping(address => uint256)) private _allowances. Asocia [propietario][gastador] con el monto permitido.
  • Eventos Canónicos (LOG3): Los eventos no mutan el storage; escriben en los recibos del bloque de la EVM mediante el opcode LOG3 (3 topics indexados).
  • Ahorro de Gas: Emitir un log cuesta ~1,500 gas vs los ~20,000 gas de una nueva escritura SSTORE. Permite que The Graph y Etherscan indexen el historial completo off-chain.
ERC20Base.sol (Solidity ^0.8.20) EVM Storage 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract ERC20Base {
    string public name;
    string public symbol;
    uint8 public immutable decimals = 18;
    uint256 public totalSupply;

    // 1. Mappings de Storage Persistente
    mapping(address => uint256) private _balances;
    mapping(address => mapping(address => uint256)) private _allowances;

    // 2. Eventos canónicos indexables (Opcode LOG3)
    event Transfer(
        address indexed from,
        address indexed to,
        uint256 value
    );
    event Approval(
        address indexed owner,
        address indexed spender,
        uint256 value
    );

    constructor(string memory _name, string memory _symbol) {
        name = _name;
        symbol = _symbol;
    }
}

6. Implementación en Código: transfer() y balanceOf()

Comprobación de saldo, deducción segura, optimización con unchecked y emisión de eventos.

Mecánica de Ejecución y Opcodes
  • balanceOf(): Función view de lectura pura en storage (SLOAD). Gratis cuando se invoca desde clientes off-chain vía RPC (eth_call).
  • Protección Dirección Cero: require(to != address(0)) previene la quema involuntaria de tokens hacia el agujero negro de la red.
  • Verificación de Solvencia: require(_balances[owner] >= value) asegura que el emisor tiene saldo suficiente antes de mutar el estado.
  • Optimización unchecked: Como el require previo ya garantiza que _balances[owner] >= value, desactivamos la verificación redundante de overflow en Solidity 0.8+ ahorrando ~120 gas.
ERC20Transfer.sol Core Logic 
// Lectura en Storage (Opcode SLOAD: 2100 gas frío / 100 caliente)
function balanceOf(address account) external view returns (uint256) {
    return _balances[account];
}

// Transferencia directa de tokens desde msg.sender
function transfer(address to, uint256 value) external returns (bool) {
    address owner = msg.sender;
    require(to != address(0), "ERC20: transfer to zero address");
    require(_balances[owner] >= value, "ERC20: insufficient balance");

    unchecked {
        // Seguro contra underflow: comprobado con require anterior
        _balances[owner] -= value;
        _balances[to] += value;
    }

    // Emisión de Opcode LOG3 (topic0: EventID, topic1: from, topic2: to)
    emit Transfer(owner, to, value);
    return true;
}

7. El Flujo Delegado: approve() y transferFrom()

La mecánica de interacción paso a paso esencial para operar con Uniswap, Lending Pools y dApps en DeFi.

Interacción con Uniswap Router
  • ¿Por qué Delegar?: Un contrato externo (como Uniswap Router) no puede descontar tokens de tu cuenta sin una autorización explícita previa.
  • Paso 1 (Usuario): Ejecuta approve(UniswapRouter, 100e18). Esto actualiza _allowances[User][Router] = 100e18.
  • Paso 2 (Llamada al Router): El usuario llama a swapExactTokensForTokens() en el Router de Uniswap.
  • Paso 3 (Extracción Atómica): El Router invoca internamente transferFrom(User, Pool, 100e18), descontando el cupo y moviendo los tokens.
  • Optimización Infinita: Si allowance == type(uint256).max, omitimos la deducción para ahorrar un SSTORE (~5,000 gas).
ERC20Delegation.sol DeFi Mechanics 
function approve(address spender, uint256 value) external returns (bool) {
    address owner = msg.sender;
    require(spender != address(0), "ERC20: approve to zero");
    _allowances[owner][spender] = value;
    emit Approval(owner, spender, value);
    return true;
}

function transferFrom(address from, address to, uint256 value) external returns (bool) {
    address spender = msg.sender;
    uint256 currentAllowance = _allowances[from][spender];
    require(currentAllowance >= value, "ERC20: insufficient allowance");

    // Optimización de Gas: No descontar si es asignación infinita
    if (currentAllowance != type(uint256).max) {
        unchecked {
            _allowances[from][spender] = currentAllowance - value;
        }
    }

    _transfer(from, to, value);
    return true;
}

8. Seguridad: Front-Running en approve() vs. EIP-2612 permit()

El exploit de modificación de allowances en el mempool y la solución atómica con firmas off-chain (EIP-712).

El Ataque de Front-Running en Mempool
  • Escenario: Alice otorgó una asignación de 100 a Bob. Decide reducirla a 50 y envía la transacción approve(Bob, 50).
  • El Ataque MEV: Bob monitorea el Mempool público, detecta la transacción pendiente de Alice y envía de inmediato transferFrom(Alice, Bob, 100) con un gasPrice superior.
  • Doble Gasto: La transacción de Bob entra primero (gasta los 100). Luego pasa la de Alice (fija 50). Bob vuelve a llamar transferFrom y gasta 50 más. Bob robó 150 en vez de 50.
  • Solución EIP-2612 permit(): Autorización con firmas off-chain (EIP-712). El usuario firma un mensaje criptográfico sin enviar transacciones previas.
ERC20Permit.sol (EIP-2612) EIP-712 Signatures 
// Aprobación atómica y sin gas on-chain previo vía firmas off-chain
function permit(
    address owner,
    address spender,
    uint256 value,
    uint256 deadline,
    uint8 v, bytes32 r, bytes32 s
) external {
    require(block.timestamp <= deadline, "ERC20Permit: expired");

    bytes32 structHash = keccak256(abi.encode(
        PERMIT_TYPEHASH,
        owner,
        spender,
        value,
        _useNonce(owner),
        deadline
    ));

    bytes32 hash = _hashTypedDataV4(structHash);
    address signer = ecrecover(hash, v, r, s);
    require(signer == owner, "ERC20Permit: invalid signature");

    _approve(owner, spender, value);
}

9. Seguridad: Desbordamiento Aritmético y el Hack BEC

Cómo una multiplicación no chequeada destruyó un token de mil millones de dólares y la protección nativa en Solidity 0.8+.

El Exploit BeautyChain (BEC) - Abril 2018
  • El Error Fatal: La función batchTransfer multiplicaba cnt * _value sin usar la librería SafeMath.
  • La Carga Maliciosa: Pasaron cnt = 2 y un valor _value = 0x8000...0000 ($2^{255}$).
  • El Desbordamiento: $$2 \times 2^{255} = 2^{256} \equiv 0 \pmod{2^{256}}$$ La variable amount se convirtió en 0.
  • El Saqueo: require(_balances[msg.sender] >= 0) pasó de inmediato. El bucle acreditó $2^{255}$ tokens de la nada a las dos cuentas del atacante.
  • Defensa Solidity 0.8+: Verificación automática de overflow con reversión nativa de opcode (Panic(0x11)).
BeautyChainExploit.sol vs Solidity 0.8+ Vulnerability Analysis 
// --- CÓDIGO VULNERABLE HISTÓRICO: BeautyChain (BEC 2018) ---
function batchTransfer(address[] _receivers, uint256 _value) public returns (bool) {
    uint cnt = _receivers.length;
    // ⚠️ DESBORDAMIENTO SILENCIOSO: 2 * 2^255 = 0 en EVM antigua
    uint256 amount = uint256(cnt) * _value;
    require(cnt > 0 && cnt <= 20);
    require(_balances[msg.sender] >= amount); // ¡PASA! (amount == 0)

    _balances[msg.sender] -= amount;
    for (uint i = 0; i < cnt; i++) {
        _balances[_receivers[i]] += _value; // ¡Acredita 2^255 tokens!
        emit Transfer(msg.sender, _receivers[i], _value);
    }
    return true;
}

// --- SOLUCIÓN MODERNA: Solidity ^0.8.0 ---
// Toda suma o multiplicación desbordada revierte automáticamente
// a nivel de opcode con código Panic(0x11), haciendo obsoleto SafeMath.

10. Seguridad: Ataque de Reentrancia y Patrón CEI

El hack de The DAO (2016) y la arquitectura defensiva Checks-Effects-Interactions con ReentrancyGuard.

Anatomía del Ataque y Patrón Defensivo
  • Mecánica del Ataque: Ocurre cuando un contrato envía fondos (call{value: ...}("")) antes de actualizar el saldo interno en storage.
  • La Trampa: El atacante intercepta la ejecución en su función fallback() o receive() y vuelve a llamar a withdraw() recursivamente.
  • Patrón CEI Obligatorio:
    1. 1. Checks: Validar saldos con require.
    2. 2. Effects: Modificar las variables de storage PRIMERO.
    3. 3. Interactions: Enviar fondos o llamar fuera AL FINAL.
  • Mutex ReentrancyGuard: Bloqueo por exclusión mutua mediante estado transitorio.
ReentrancyDefense.sol CEI Pattern 
// ❌ VULNERABLE: Efecto después de llamada externa
function withdrawBad() external {
    uint256 bal = balances[msg.sender];
    require(bal > 0);
    (bool s, ) = msg.sender.call{value: bal}("");
    require(s);
    balances[msg.sender] = 0; // ¡Tarde! El atacante ya reingresó
}

// ✅ SEGURO: Patrón Checks-Effects-Interactions + Mutex
function withdrawSafe() external nonReentrant {
    // 1. CHECKS
    uint256 bal = balances[msg.sender];
    require(bal > 0, "Sin saldo");

    // 2. EFFECTS (Actualizar estado antes de llamar fuera)
    balances[msg.sender] = 0;

    // 3. INTERACTIONS (Llamada externa al final)
    (bool success, ) = msg.sender.call{value: bal}("");
    require(success, "Transfer failed");
}

11. Arquitectura Profesional: OpenZeppelin v5

La función centralizada _update(), modularidad con extensiones y control de acceso Ownable2Step.

La Revolución de _update() en OZ v5
  • Hook Unificado: En OpenZeppelin v5 desaparecieron los viejos hooks _beforeTokenTransfer y _afterTokenTransfer.
  • Canalización Central: Todas las transferencias, acuñaciones (mint) y quemas (burn) se canalizan a través de un único método virtual: _update(address from, address to, uint256 value).
  • Menor Costo de Gas: Reduce saltos internos y facilita la sobreescritura limpia para añadir listas negras, pausabilidad o snapshots de gobernanza.
  • Extensiones Modulares: Integración composable con ERC20Burnable, ERC20Pausable y Ownable2Step.
UdeAToken.sol (OpenZeppelin v5) OZ v5 Architecture 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Pausable.sol";
import "@openzeppelin/contracts/access/Ownable2Step.sol";

contract UdeAToken is ERC20, ERC20Burnable, ERC20Pausable, Ownable2Step {
    constructor(address initialOwner) 
        ERC20("UdeA Blockchain Token", "UDEA") 
        Ownable(initialOwner) 
    {
        _mint(initialOwner, 1_000_000 * 10 ** decimals());
    }

    function pause() external onlyOwner { _pause(); }
    function unpause() external onlyOwner { _unpause(); }

    // Sobrescritura obligatoria del hook central de OpenZeppelin v5
    function _update(address from, address to, uint256 value)
        internal
        override(ERC20, ERC20Pausable)
    {
        super._update(from, to, value);
    }
}

12. Anomalías en Producción: USDT y Fee-on-Transfer

Omisión de retorno booleano en contratos antiguos, la solución SafeERC20 y tokens con impuestos en DeFi.

El Caso USDT (Tether) y SafeERC20
  • El Pecado Original de USDT: El contrato desplegado en 2017 (0xdac17f...) omitió returns (bool) en transfer y approve.
  • Fallo en Compiladores Modernos: Si compilas con la interfaz IERC20, Solidity comprueba returndatasize() == 32. Al recibir 0 bytes, ¡la transacción revierte!
  • Solución SafeERC20: Inspecciona en bajo nivel con ensamblador; tolera tanto retorno vacío (como USDT) como booleanos verdaderos.
  • Tokens con Comisión (Fee-on-Transfer): Restan un % de impuestos al transferir. Se debe medir balanceAfter - balanceBefore.
ProductionVault.sol (SafeERC20) Defensive DeFi 
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract ProductionVault {
    using SafeERC20 for IERC20;

    // ✅ 1. Manejo seguro de USDT y retornos no estándar
    function safeDeposit(IERC20 token, uint256 amount) external {
        // safeTransferFrom admite returndata vacío (USDT) o true
        token.safeTransferFrom(msg.sender, address(this), amount);
    }

    // ⚠️ 2. Manejo de tokens con comisión (Fee-on-Transfer)
    function depositFeeToken(IERC20 token, uint256 amount) external {
        uint256 balBefore = token.balanceOf(address(this));
        token.safeTransferFrom(msg.sender, address(this), amount);
        uint256 balAfter = token.balanceOf(address(this));

        uint256 actualReceived = balAfter - balBefore;
        require(actualReceived > 0, "No tokens received");
        _creditUser(msg.sender, actualReceived);
    }
}

14. Estándar ERC-721: Tokens No Fungibles (NFTs)

Unicidad criptográfica, metadatos JSON descentralizados y emisión de títulos universitarios verificables.

Arquitectura y Caso de Aplicación UdeA
  • Propiedad Única: Cada token posee un tokenId de 256 bits irrepetible. El contrato mapea tokenId => address owner.
  • Metadatos Off-Chain: tokenURI(tokenId) resuelve a una URI en IPFS (ipfs://...) con un JSON canónico con nombre, calificaciones y actas.
  • Transferencias Seguras: safeTransferFrom verifica que el contrato receptor implemente onERC721Received para no atrapar el token.
  • Caso de Aplicación UdeA: Emisión de Diplomas de Grado y Certificados de la Facultad de Ingeniería verificables al instante por empleadores de todo el mundo sin intermediarios.
IERC721.sol (EIP-721 Interface) Non-Fungible 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/utils/introspection/IERC165.sol";

interface IERC721 is IERC165 {
    event Transfer(address indexed from, address indexed to, uint256 indexed tokenId);
    event Approval(address indexed owner, address indexed approved, uint256 indexed tokenId);
    event ApprovalForAll(address indexed owner, address indexed operator, bool approved);

    function ownerOf(uint256 tokenId) external view returns (address owner);
    function balanceOf(address owner) external view returns (uint256 balance);

    function safeTransferFrom(
        address from, address to, uint256 tokenId, bytes calldata data
    ) external;

    // Metadatos descentralizados (IPFS / Arweave)
    function tokenURI(uint256 tokenId) external view returns (string memory);
}

15. Estándar ERC-1155: Multi-Token Semi-Fungible

Tokens fungibles y no fungibles en un solo contrato con ahorro masivo de hasta el 80% en costos de gas.

Eficiencia Masiva y Aplicación Institucional
  • Contrato Multipropósito: Un único contrato gestiona una cantidad infinita de tipos de tokens diferenciados por un uint256 id.
  • Operaciones en Lote (Batch): Transfiere múltiples tipos de tokens y cantidades en una sola transacción atómica, ahorrando hasta 80% de gas frente a ERC-721.
  • URI Parametrizada: Sustituye el {id} en la URI de IPFS evitando guardar cadenas de texto pesadas en storage.

16. Estándar ERC-4626: Tokenized Yield Vaults

Bóvedas de rendimiento financiero estandarizadas y matemáticas de conversión entre activos y acciones.

Mecánica de Acciones y Activos
  • Fin a la Fragmentación: Antes de ERC-4626, Yearn (yVaults), Compound (cTokens) y Aave (aTokens) tenían interfaces incompatibles.
  • Bóveda como Token ERC-20: ERC-4626 hereda de ERC-20. Depositas un activo base (asset, ej. USDC) y recibes participaciones (shares).
  • Matemática de Conversión: $$\text{shares} = \text{assets} \times \frac{\text{totalSupply()}}{\text{totalAssets()}}$$
  • Caso de Aplicación UdeA: Bóvedas automatizadas para el Fondo de Tesorería e Investigación de la UdeA, generando rendimiento auditado en tiempo real on-chain.

17. Estándar ERC-3643: Tokens Regulados y Tokenización RWA

Arquitectura T-REX para Activos del Mundo Real: Identidad on-chain, cumplimiento normativo y transferencias condicionadas.

Tokenización Institucional y Marco Legal
  • Más allá del ERC-20: Activos del mundo real (RWA: bonos, acciones, bienes raíces) no pueden transferirse libremente; la ley exige KYC y AML estricto.
  • Identidad ONCHAINID: Contratos de identidad que verifican credenciales criptográficas de los inversores sin publicar datos privados en la red.
  • Motor de Cumplimiento (Compliance): Antes de cada transferencia, el contrato verifica automáticamente límites por país y estatus de acreditación.
  • Caso de Aplicación UdeA / RWA: Tokenización de Bonos del Tesoro (T-Bills) y fraccionamiento fiduciario de infraestructura tecnológica universitaria con plena validez jurídica.
